# Green web observability

This is the production web configuration for `interoves-web-green-lb`. The
current environment is Amazon Linux 2023 / Python 3.12, uses `systemd` and
`web.service` (Daphne), has two `t3.small` instances at present, and publishes
EC2 CPU metrics at the default five-minute interval. Green already streams
`web.stdout.log`, Nginx access/error logs, and EB engine/hooks logs to CloudWatch
Logs with 14-day retention and `DeleteOnTerminate: false`.

Before this configuration is applied, the Green postdeploy hook skips the web
role, no `InterOves/Web` custom metrics are present, and no systemd/kernel log
groups exist. The production ALB has access logs disabled. Existing ALB alarms
were attached to a previous load balancer/target group; the apply script
resolves the current Green resources from Elastic Beanstalk and updates the
existing alarm names in place. It uses the already-configured
`interoves-eb-health-alerts` SNS topic.

## What is collected

- Kernel journal messages at info priority (includes kernel OOM-killer lines).
- systemd manager lifecycle/failure messages, `systemd-oomd`, and CloudWatch
  Agent warnings. Daphne stdout/stderr remains in the existing EB
  `web.stdout.log` stream; it is not copied into another log group.
- Per-instance and Auto Scaling group metrics every 60 seconds: CPU, used and
  available memory, swap used percentage, root filesystem used percentage and
  free bytes, and Daphne process count. EC2 detailed monitoring is not enabled.
- Nginx request method/path, status, total and upstream timing, target address,
  Nginx request ID, Django `X-Request-ID`, hostname, and ALB
  `X-Amzn-Trace-Id`. Query strings and response bodies are excluded.
- Slow Django requests on every route, with safe path, method, status, elapsed
  time, request ID, hostname and process ID. Existing named phase timing stays
  limited to its current watched endpoints. Request bodies and query strings
  are not logged.

System logs use per-instance streams and 14-day retention. The existing EB log
groups retain their current 14-day policy and survive instance termination.

## Apply sequence

1. Review the plan without changing AWS:

   ```bash
   ./scripts/apply_green_observability.sh --plan
   ```

2. During an approved infrastructure change, apply the two log groups, the
   least-privilege web instance role policy, metric filters and alarms:

   ```bash
   ./scripts/apply_green_observability.sh --apply
   ```

   This does not deploy the application or enable ALB access logs. It creates
   only `/systemd` and `/kernel` CloudWatch log groups, grants the EC2 role
   write access to those streams and `InterOves/Web` metrics, then upserts
   alarms. Existing alarms are rebound to the current Green ALB and target
   group. All alarm actions use the existing SNS topic.

3. Deploy the application bundle with the regular Green deploy process. The
   Green bundle builder explicitly overlays the reviewed CloudWatch Agent hook
   and Nginx timing format because it otherwise preserves live `.platform`
   files. On every new/replaced web instance the hook installs this agent
   config and restarts the agent; worker behavior remains on its existing
   config.

4. Verify the new instance streams under the two log groups, metrics in
   `InterOves/Web`, alarm dimensions, Nginx-to-Django request IDs and the
   successful `/health/live/` target checks. The environment's minimum
   capacity may be one instance, so there is intentionally no alarm that
   expects two healthy targets at all times.

The script defaults to read-only `--plan`; it does not run during deployment.
The AWS changes and the application deployment are separate operations so the
IAM/log groups can be prepared before the new hook is deployed.

## Alarms

- ALB-generated 502 and 504: 3 or more in five minutes. These use
  `HTTPCode_ELB_*_Count`, which separates errors generated by ALB from target
  responses.
- Target-generated 5xx: 3 or more in five minutes.
- At least one unhealthy target for three of five one-minute periods; zero
  healthy targets for three consecutive minutes, including missing data.
- Memory at or above 85% for two of three one-minute periods; root free space
  below 1 GiB for two of three periods; CPU at or above 90% for three of five
  one-minute periods.
- Kernel OOM-kill evidence and systemd `web.service` process failure events.

The alarm count thresholds filter isolated errors while still catching the
October incident (9 and then 19 ALB-generated 504s in successive minutes).
The existing notification topic and its current subscribers are reused.

## ALB access log privacy decision

Native ALB access logs include the full request line, including query strings.
The application has OAuth callback URLs containing short-lived `code` values.
The ALB cannot redact those values before writing the log, so native ALB access
logs are deliberately not enabled. The ALB's 502/504 metrics identify the
failure layer and count; Nginx logs provide safe request paths and trace IDs
when the target receives the request. If a future requirement needs the URI for
requests that never reach Nginx, it needs an approved design that prevents raw
OAuth query values from being retained.

Enabling native ALB logs also requires a same-region S3 bucket using SSE-S3 and
a bucket policy for the ELB log delivery service. It adds S3 storage and
request costs; AWS does not charge ELB bandwidth for delivery. This is a
separate infrastructure change and is not included in the apply script.

## Cost and limitations

The agent publishes eight metric types with per-instance and Auto Scaling group
dimensions. With two active instances, that is up to 24 metric series; the two
event metrics add up to two more when they emit data. At the current first tier
of about $0.30 per custom metric, budget up to $7.80/month for these metrics.
Seven standard alarms are new (about $0.70/month at $0.10 each); three existing
alarms are updated in place. This is roughly $8.50/month before account
allowances. No one-minute EC2 detailed monitoring charge is added. Kernel and
systemd log ingestion is usage-based; plan around $0.50 per additional GB
ingested, with the exact CloudWatch Logs rate and any account allowance
determined by the AWS bill. The systemd/kernel filters keep volume bounded; the
existing app and Nginx log volume is unchanged apart from a few safe fields per
Nginx request.

The agent normally forwards journal events promptly, but no remote log system
can guarantee delivery if an instance is terminated abruptly before its local
buffers are sent. CloudWatch Logs retention also does not make application
logs a complete request ledger. ALB access logs are best-effort and, under the
privacy constraint above, remain disabled. Thus a 504 produced before a target
accepts the request can still lack a URL/path; its ALB status, target
connection/timing fields, time and target IP are available only if raw ALB
logs are later approved, while current ALB metrics at least preserve status
counts.

`ai-bot` retains `AWS-RunShellScript` access only on instances with the Green
environment tag. Because the role already has an unconditioned allow for the
AWS-owned `AWS-RunShellScript` document, adding a Green instance grant gives
root-shell capability on those instances. IAM evaluates the document and
instance resources separately, so a tag condition on a custom document grant
does not make that shell read-only. Narrowing further requires changing the
role's existing document grant and its other diagnostic target permissions;
that could affect existing Blue/worker workflows and is outside this
observability configuration.
