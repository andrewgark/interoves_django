# План: проверка заданий на клиенте и офлайн-режим

Статус: план согласован 2026-10-29. Сделано: R1, R2 и R4 фазы 0 (см. отметки ниже).

Цель — страницы с заданиями отвечают мгновенно и продолжают работать без сети, а
сервер нужен только для синхронизации. Минимум — ежедневная Лесенка и проверка
слов; максимум — все типы заданий, где это осмысленно, включая подсказки.

Главное требование к коду: **не переписывать серверные проверки на JS**. Фронт
получает от сервера *данные*, по которым умеет проверять один маленький
универсальный интерпретатор, а то немногое, что всё-таки существует в двух
языках, закрыто общими контрактными фикстурами.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Кто авторитетен | Сервер. Клиентский вердикт предварительный; очки, прогресс, время и завершение считает сервер при синхронизации. При расхождении побеждает сервер, клиент перекатывает неотправленные события поверх его состояния. |
| Утечка ответов | Для ежедневных игр допустима (как в Wordle). Хэши ответов — защита от случайного спойлера в devtools, не от перебора. Турниры по умолчанию онлайн. |
| Время офлайн | Доверяем клиентским замерам с ограничениями здравого смысла (раздел «Время»). |
| Командный режим | Только онлайн. Ограничение в коде, не в конфиге. |
| Подсказки офлайн | Не в первой итерации; архитектура оставляет под них место (фаза 5). |
| Управление | Конфиг правил в админке + аварийный выключатель в env (раздел «Конфиг»). |
| Ошибки | Структурные логи; важное — в Telegram админу через существующую очередь алертов (раздел «Наблюдаемость»). |

## Архитектура

```
 сервер                                              браузер
 ───────                                             ───────
 Checker.client_spec() ─┐                            offline_verify.js   (интерпретатор spec)
 Puzzle reducer config ─┼─> task pack (JSON) ──────> offline_reducer_<type>.js (переходы состояния)
 OfflinePolicy resolve ─┘        │                   offline_outbox.js   (IndexedDB, события)
                                 │                   offline_sync.js     (пачки, повторы)
 /play/sync  <───────────────────┼────────────────── события {client_event_id, ...}
   └─ цикл по существующим сервисам (check_attempt, hint, ui_state, timing)
   └─ ответ: вердикт по событию + авторитетный snapshot
```

### 1. Операции нормализации — один словарь на двух языках

Сейчас нормализация размазана по декораторам `@clean`, `@clean_but_ё_stays`,
`@delete_spaces`, `@delete_punctuation`, `@delete_punctuation_metagram`
(`games/puzzles/core/check_runtime.py`) и функциям `raddle_word_core`,
`salad.rules.normalize_word`, `alphabetty.core.normalize_word`.

Становится реестром именованных операций:

```
games/puzzles/core/normalize_ops.py   # 'lower', 'yo_to_e', 'strip', 'drop_spaces',
                                      # 'drop_punct', 'drop_punct_metagram', 'raddle_core', ...
static/js/offline_normalize.js        # те же имена, та же семантика
contracts/normalize.json              # [{"ops": [...], "in": "...", "out": "..."}]
```

Серверные чекеры объявляют конвейер (`NORMALIZE = ('lower', 'yo_to_e',
'drop_punct')`) вместо стопки декораторов, поэтому одноимённая операция по
построению одна и та же на сервере и клиенте. Фикстура обязана покрывать
известные различия Python и JS: `str.lower()` против `toLowerCase()` на
нестандартных буквах, `\w`/`\s` в `re` (Unicode по умолчанию) против JS (нужен
флаг `u` и `\p{L}`), `ё`/`Ё`, неразрывные пробелы, тире разных видов.

### 2. Описание проверки (`client_spec`) — данные, а не код

`BaseChecker.client_spec(self, task) -> dict | None`. `None` (по умолчанию) —
задача проверяется только онлайн; так переход идёт по одному типу заданий за раз.

```json
{"kind": "hash_set", "ops": ["lower", "yo_to_e", "drop_punct"],
 "salt": "<task_id>:<attempt_revision>", "accept": ["9f2c…", "41ab…"]}
```

| `kind` | Чекеры |
|---|---|
| `hash_set` | equals, several_answers, equals_with_possible_spaces, any_answer, белый список white_gray_black, слова raddle |
| `hash_set_per_word` | norm_matcher: сервер разворачивает формы ответа через pymorphy (`parse.lexeme`) и отдаёт хэши по позициям; pymorphy на клиенте не нужен |
| `number_range` | number_with_error |
| `regex` | regexp, только если выражение прошло проверку JS-совместимости при сохранении задачи |
| `composite` | многоячеечные задания (wall, grid, replacements): именованные дочерние spec |

Хэш — SHA-256 через `crypto.subtle` (есть в secure context, т.е. на https и
localhost). Интерпретатор `static/js/offline_verify.js` ~150 строк; новый тип
задания почти всегда = новый `client_spec()` на Python без изменений в JS.

### 3. Переходы состояния — единственное честное дублирование

Проверить слово легко; сложнее, что после этого происходит: `solved_indices`,
`playable_word_indices`, `used_hints`, ступени ассиста, подстановка соседнего
слова в текст подсказки (`render_raddle_clue`). Это надо уметь на клиенте.

Подход: выделить на Python чистую функцию перехода
`apply_move(state, parsed, word_index, is_correct) -> MoveOutcome` и её JS-зеркало,
связанные фикстурами:

```
contracts/raddle/*.json      # initial_state + events -> ожидаемые state и вердикты
```

Фикстуры по возможности *генерируются* прогоном настоящего Python-движка по
сценариям (management-команда), node-тест сравнивает с ними JS. Очки (`total`,
`word_solve_credit`) в JS-переход **не** входят — клиент показывает только
прогресс, баллы приходят с сервера. Так зеркалится минимально возможная
поверхность, и прецедент уже есть: `raddle/contract.py` ↔ `raddle_state.js`.

### 4. Пакет задания (task pack)

Встраивается в страницу как `<script type="application/json" id="offline-pack">`
и доступен отдельно (`GET /play/pack/<game>/<task_group>/`) для Service Worker:

```
{ v, game_id, task_group_id,
  tasks: [{ task_id, task_type, attempt_revision, spec, reducer_config, quota }],
  state_snapshot, capabilities, issued_at, pack_token }
```

- `attempt_revision` уже есть на `Task`: если задачу отредактировали, sync
  отвечает «пакет устарел», клиент обновляет пакет (семантика как у
  `reload_required`).
- `capabilities` — результат конфига (раздел «Конфиг») на момент выдачи.
- `pack_token` — Django-signed: actor (как в `gameplay_context`), game,
  task_group, `issued_at` (серверное время), версия политики. Сервер на sync
  верит только подписанному `issued_at` — это якорь для ограничения времени.
- `quota` — лимит попыток/опечаток, чтобы клиент не давал офлайн больше, чем
  примет сервер.

### 5. Очередь событий и синхронизация

Событие:

```
{ client_event_id: uuid, pack_token, task_id, attempt_revision,
  type: "attempt" | "hint" | "ui_state" | "timing",
  payload, client_seq, client_verdict, mono_ms }
```

- **Хранение:** IndexedDB, отдельное хранилище на актора. Смена аккаунта →
  чужая очередь не отправляется под новым актором (как `reload_required`).
- **`POST /play/sync`:** пачка событий по порядку. Новой игровой логики нет —
  цикл вызывает существующие сервисы (`check_attempt`, `create_hint_attempt`,
  `accept_ui_draft`, timing). Ответ: вердикт по каждому событию
  (`accepted | duplicate | rejected:<code> | stale_pack`) и авторитетный
  snapshot.
- **Идемпотентность:** отдельная таблица `OfflineEventReceipt(client_event_id
  unique, actor, kind, attempt FK null, hint_attempt FK null, client_seq,
  received_at, outcome)` — без миграции большой таблицы `Attempt`. Тот же ключ
  используют и обычные онлайн-эндпоинты (фаза 0), что снимает текущее
  ограничение из `agents/raddle.md` «abort не авто-ретраится».
- **Вкладки:** очередь отправляет одна вкладка (Web Locks API), остальные
  узнают об изменениях через `BroadcastChannel`.
- **Сохранность:** Safari может удалить IndexedDB через ~7 дней без
  взаимодействия, поэтому очередь отправляется при первом появлении сети
  (`online`, `visibilitychange`, старт страницы), а не «когда-нибудь».
- **Расхождение:** `client_verdict` сравнивается с серверным. Расхождение —
  баг spec/reducer (или подделка); логируется и алертится (раздел
  «Наблюдаемость»), клиент принимает серверное состояние.

### 6. Отрисовка

Полный переход на клиентский рендер не нужен. Сервер рендерит разметку со всеми
строками; клиент по результату перехода переключает классы и подставляет тексты
(решённое слово он знает — его ввёл игрок; шаблоны подсказок с местом для слова
лежат в `reducer_config`). При sync серверный HTML, как и сейчас, применяется
только при явном сигнале продвижения — главный принцип из `agents/raddle.md`
сохраняется.

### 7. Офлайн-оболочка

`static/sw.js`: кэш статики и страниц сегодняшних ежедневных игр с их пакетами.
Завтрашние пакеты заранее не качаются (спойлеры, смена дня). Версия кэша
привязана к версии деплоя (`deploy_version_check.js`); при смене версии SW
обновляет кэш, но **не** трогает IndexedDB с очередью.

## Конфиг: что включено, где и для кого

### Модель

`games/models/offline.py`, правка в админке:

```
OfflinePlayRule
  enabled           bool
  task_type         str | null      # 'raddle', 'equals', ... ; null = любой
  section           FK | null       # раздел ежедневных игр
  game              FK | null       # точечное правило для одной игры
  mode              'general' | 'tournament' | 'replay' | null
  instant_verdict   bool            # мгновенный вердикт при наличии сети
  offline_attempts  bool            # попытки без сети через очередь
  offline_timing    bool            # время офлайн-интервалов засчитывается
  offline_hints     bool            # фаза 5
  rollout_percent   0..100          # стабильно по HMAC актора
  note              text
  updated_at
```

### Разрешение

`games/offline/policy.py: resolve_capabilities(game, task, mode, actor) ->
OfflineCapabilities` — чистая функция над списком правил:

1. `settings.OFFLINE_PLAY_ENABLED` (env, по образцу
   `GAMEPLAY_CONTEXT_REQUIRE_TOKEN`) выключен → всё выключено.
2. Жёсткие ограничения кода, конфиг их не снимает: командный актор → онлайн;
   `client_spec() is None` → нет `instant_verdict`/`offline_attempts` для этой
   задачи.
3. Из подходящих правил выигрывает самое специфичное (game > section >
   task_type > mode > глобальное); при равенстве — более позднее.
4. `rollout_percent` — по стабильному хэшу актора, чтобы игрок не «мигал»
   между режимами.
5. Зависимости флагов: `offline_attempts` ⇒ `instant_verdict`;
   `offline_timing` и `offline_hints` ⇒ `offline_attempts`.

Правила кэшируются (версия в cache, сбрасывается сигналом `post_save`). Итог
вшит в `pack_token`: сервер принимает событие, если оно было разрешено пакетом,
под которым его сделали. Выключение правила останавливает выдачу новых пакетов,
но честно сыгранное офлайн не теряется. Аварийный выключатель жёстче: при нём
sync отклоняет офлайн-события, кроме обычных попыток.

Админка показывает «эффективные возможности» для выбранной игры/задачи, чтобы
было видно итог разрешения, а не только список правил.

## Время офлайн

Опирается на существующий механизм `client_credit_ms` из
`docs/daily-timing-architecture.md` (ограниченное начисление по заявке клиента)
и обобщает его. Только личный актор.

- Клиент пишет в очередь события `timing` вида `offline_interval {session_id,
  seq, mono_start, duration_ms}`. Длительность — по `performance.now()`
  (монотонно, не зависит от часов устройства); копится только пока вкладка
  видима и не на паузе, интервал режется по тому же idle-пределу, что и сейчас.
- Сервер (новое действие `offline_interval` в `DailyTimingEvent`, тот же
  replay-редьюсер) начисляет с ограничениями:
  - сумма офлайн-интервалов ≤ `received_at − issued_at` подписанного пакета
    минус уже подтверждённое сервером время в этом промежутке;
  - каждый интервал ≤ idle-предел; интервалы с перекрытием по `seq`
    отбрасываются;
  - общий предел игры — существующие 12 часов;
  - если в этот промежуток онлайн-сессия актора уже подтверждала активность,
    пересечение не начисляется (как в `client_credit_ms`).
- Начисленное складывается в `client_credited_ms` и в новое
  `offline_credited_ms` — видно в лидерборде/админке, логируется
  `daily_timing_offline_credit`.
- Завершение игры происходит на сервере в момент sync финальной попытки;
  `frozen_ms` считается из журнала с офлайн-интервалами. Клиент до этого
  показывает предварительное время и пометку «синхронизируется».

## Наблюдаемость

### Что считаем ошибками

| Событие | Где фиксируется | Уровень | Telegram |
|---|---|---|---|
| `offline_verdict_divergence` — клиент сказал «верно», сервер «неверно» или наоборот | сервер на sync | critical | да, dedupe по (task_type, task_id) на час |
| `offline_pack_build_failed` — `client_spec()` упал на задаче | сервер при выдаче пакета | critical | да, со ссылкой на задачу в админке |
| `offline_reducer_divergence` — состояние клиента после sync ≠ серверного | сервер | error | да, агрегатом |
| `offline_sync_rejected` — stale_pack, actor mismatch, quota, policy | сервер | warning | только при всплеске |
| `offline_outbox_stale` — события старше N часов в очереди при отправке | сервер по `client_seq`/возрасту | warning | при всплеске |
| `offline_timing_clamped` — заявка времени урезана ограничениями | сервер | info | нет (в дайджест) |
| `offline_storage_unavailable`, `offline_sw_error`, `offline_crypto_unavailable` | клиент → телеметрия | info | нет |

### Как устроено

- **Сервер:** логгер `games.offline`, структурные события в стиле
  существующих (`daily_timing_client_credit`, `gameplay_attempt_created`):
  request ID, actor namespace, task, тип, код. **Без ответов, текстов попыток и
  содержимого подсказок** — правило из `docs/gameplay-security.md`.
- **Клиент:** `offline_telemetry.js` — кольцевой буфер в IndexedDB (≤200 записей),
  отправляется вместе с sync или `sendBeacon` на `/play/telemetry`. Эндпоинт
  ограничен по размеру и частоте и считает вход недоверенным.
- **Telegram:** новые `notify_admin_offline_*` в
  `games/ops/telegram/bot/notify.py` через существующий
  `_deliver_admin_text(..., delivery='queue', dedupe_key=...)`. Алерты строятся
  только из того, что посчитал сервер (расхождение он вычисляет сам из
  `client_verdict` и своего вердикта), поэтому клиент не может «нарисовать»
  алерт; дополнительно порог и dedupe на актора против спама подделанными
  `client_verdict`.
- **Всплески:** счётчики в Redis по (код, час); алерт при превышении порога.
  Ежедневный дайджест (число офлайн-sync, отклонений, урезаний времени) — через
  существующий cron в `games/ops/cron`.

## Применимость по типам

| Тип | Клиентская проверка | Переход состояния | Замечание |
|---|---|---|---|

| equals / several_answers / spaces / number / any_answer | да | не нужен | почти бесплатно после фазы 1 |
| white_gray_black | белый список | — | серый список — онлайн-досверка |
| norm_matcher | `hash_set_per_word` | — | проверить объём для длинных ответов |
| regexp | при JS-совместимом выражении | — | валидация при сохранении |
| wall, grid-* | `composite` | нужен | средняя сложность |
| replacements_lines / html_forms | да | — | `replacements_input_parse.js` уже дублирует Python — перевести на контракт |
| word_salad | словарь 156 КБ gz | нужен | реально |
| alphabetty | словарь 4.6 МБ | — | только ленивой загрузкой при включённом офлайне, иначе онлайн |

| metagram, long_string, hangman, antiwordle, solutions_tag_number | нет | — | редкие, онлайн |

## Фазы

Каждая фаза самостоятельно полезна и выкатывается отдельно.

### Фаза 0 — предварительный рефакторинг (без видимых изменений)

- **R1. Реестр нормализации.** `normalize_ops.py`; чекеры, `raddle_word_core`,
  `salad`/`alphabetty` `normalize_word` переходят на именованные конвейеры.
  Поведение не меняется — подтверждается существующими тестами плюс
  `contracts/normalize.json`, прогоняемым на Python.
  **Сделано:** `games/puzzles/core/normalize_ops.py` (декоратор
  `@normalized(...)`, конвейеры `CLEAN`, `CLEAN_KEEP_YO`, `RADDLE_WORD`),
  JS-двойник `static/js/offline_normalize.js`, общий
  `contracts/normalize.json`. Через реестр идут `clean_text`,
  `raddle_word_core` и все чекеры `check_runtime`/antiwordle.
  `normalize_word` Салатика и Алфавитки (верхний регистр, свой алфавит)
  перейдут на реестр в фазе 4 вместе с их `client_spec`. Найденные
  расхождения Python/JS (набор пробельных символов, `re.I` для `İ ı ſ K`)
  учтены в JS и закреплены фикстурой.
- **R2. Разделить вердикт, переход и очки в `RaddleChecker.check`.** Сейчас
  один метод проверяет индекс/маску, меняет `solved_indices`/`used_hints` и
  считает `total`. Выделить `raddle/transition.py: apply_move(...)` и
  `score(...)`; чекер становится склейкой. Тот же шаблон позже для wall.
  **Сделано:** `games/puzzles/raddle/transition.py` — `refuse_word`,
  `advance`, `progress_status` (будут зеркалиться в JS) и `score_word`
  (только сервер). `RaddleChecker.check` — разбор посылки и склейка этих
  функций; результат совпал со старым кодом на 20 000 случайных
  состояний/ходов.
- **R3. Игровая мутация без `request`.** Ядро `process_send_attempt(request,
  task_id)` (разбор, актор, режим, `check_attempt`, сборка ответа) выделить в
  сервис `submit_move(actor_ctx, task, game, move, *, client_event=None)`;
  view — тонкая обёртка над ним. Это нужно `/play/sync`, чтобы не копировать
  view. То же для подсказок (`process_send_hint_attempt`) и `ui_state`.
- **R4. Идемпотентность онлайн-отправок.** `OfflineEventReceipt` +
  необязательный `client_event_id` в `send_attempt` Лесенки. В
  `raddle_state.js` `classifyRequestFailure` разрешает повтор после abort, если
  ключ есть. Полезно сразу, независимо от офлайна.
  **Сделано:** модель `ClientEventReceipt` (без актора — повтор принимается,
  пока Attempt принадлежит текущему актору, это переживает merge anon →
  user), `games/site/session/client_events.py`, поиск квитанции до проверки
  «не playable» и под блокировкой в `check_attempt`, уникальный ключ как
  страховка от гонки. Ответ на повтор собирается тем же `_move_response`, что
  и обычный ход. Генератор UUID общий с таймером: `static/js/client_event_id.js`.
  Ограничение: повтор не запускает завершение игры заново — если первый
  запрос записал ход, но упал до завершения, игра завершится на следующем ходе
  (как и при обычном дубликате).
- **R5. Инфраструктура контрактов.** Каталог `contracts/`, хелпер загрузки для
  pytest, node-хелпер. Новые JS-модули — плоско `static/js/offline_*.js`, чтобы
  их подхватил `games/tests/test_js_suites.py` (он берёт только
  `static/js/*.test.js`).
- **R6. Протокол `client_spec()`** в `BaseChecker` (по умолчанию `None`) и
  реализации для простых чекеров + raddle; тест, что для каждого фикстурного
  ответа spec, исполненный Python-реализацией интерпретатора, совпадает с
  `check()`.

Критерий готовности: полный `./run_tests.sh` зелёный, на проде ничего не
поменялось, `OfflineEventReceipt` пишется на онлайн-попытках Лесенки.

### Фаза 1 — мгновенный вердикт Лесенки (ещё онлайн)

- `OfflinePlayRule` + `resolve_capabilities` + админка; `OFFLINE_PLAY_ENABLED`.
- Пакет в странице, `offline_normalize.js`, `offline_verify.js`.
- Клиент сразу красит строку «верно/неверно», запрос уходит в фоне с
  `client_verdict`; на сервере уже работает `offline_verdict_divergence` и алерт.
- Выкатка через `rollout_percent`: 5% → 50% → 100%, смотрим расхождения.

Критерий: неделя на 100% ежедневной Лесенки без расхождений.

### Фаза 2 — офлайн-Лесенка (личный ежедневный режим)

- `offline_outbox.js`, `offline_sync.js`, `/play/sync`, Web Locks/BroadcastChannel.
- `offline_reducer_raddle.js` + `contracts/raddle/*.json` (генерация из Python).
- Офлайн-время (`offline_interval`, `offline_credited_ms`).
- `static/sw.js`, пакет по отдельному URL.
- UI-статус: «офлайн, N ходов ждут отправки» / «синхронизировано» / «расхождение,
  обновлено с сервера».
- Телеметрия клиента, дайджест.

Критерий: e2e — открыть страницу, отключить сеть, решить, закрыть вкладку,
открыть снова, включить сеть → результат, время и завершение на сервере
корректны; повторная доставка той же пачки ничего не дублирует.

### Фаза 3 — простые чекеры во всех ежедневных играх

`client_spec()` для equals-семейства, number, norm_matcher, regexp (с проверкой
совместимости при сохранении задачи); переходы не нужны. Включается правилами
по `task_type`/разделу.

### Фаза 4 — составные задания

wall, grid, replacements, word_salad — по одному типу, каждый с R2-подобным
выделением перехода и своими контрактными фикстурами. alphabetty — если
ленивая загрузка словаря окажется приемлемой по размеру.

### Фаза 5 — подсказки офлайн (на будущее)

Что понадобится, оценка — «средне, после фазы 2 недорого»:

- в пакет (только при `offline_hints`) кладутся тексты подсказок, слегка
  обфусцированные (защита от случайного спойлера, не криптография); для
  ассиста Лесенки с открытием слова — каноническое слово, т.к. хэша мало;
- событие `hint` в очереди; на sync — существующий `create_hint_attempt`,
  штраф считает сервер;
- переход состояния уже чистый (`apply_assist_tier`, `resolve_assist_tiers`) —
  добавляется в JS-зеркало и фикстуры;
- правило `need_clue_first`/`duplicate` из `assist_block` — тоже в фикстуры.

### Фаза 6 — командный режим (не планируется сейчас)

Требует слияния офлайн-ходов нескольких участников поверх `select_for_update` и
realtime; отдельный проект.

## Риски

| Риск | Мера |
|---|---|
| Python и JS разошлись в нормализации/переходах | контрактные фикстуры в CI + алерт о расхождении в проде + сервер авторитетен |
| Задачу отредактировали после выдачи пакета | `attempt_revision` в событии → `stale_pack`, клиент обновляет пакет и перекатывает очередь |
| Потеря очереди (Safari, очистка данных) | немедленная отправка при сети; UI честно показывает неотправленное |
| Две вкладки/устройства одного актора | Web Locks на вкладки; между устройствами — сервер авторитетен, дубли гасит `client_event_id` и существующая детекция дубликатов |
| Смена аккаунта при непустой очереди | очередь привязана к актору, под другим не отправляется; anon→user merge — отдельно проверить вместе с `anon_merge_poll_lease.js` |
| Накрутка времени | ограничения по подписанному `issued_at`, idle-предел, 12 ч, пересечения с онлайн-сессиями; `offline_credited_ms` видно в лидерборде |
| Подделанный `client_verdict` для спама алертами | алерты только из серверного вычисления, порог и dedupe на актора |
