# Командный таймер: параллельное решение на нескольких устройствах

Статус: предложение к реализации, 2026-10-01.

## Проблема

Сейчас для командного режима у `DailySolveTiming` одна общая строка и один
`active_session_id`. Первый открывший страницу получает право вести таймер,
остальные страницы видят `is_authoritative=false` и показывают блокирующий экран
«Игра открыта в другой вкладке».

Это корректно для защиты от двух вкладок одного личного решения, но неверно для
команды: участники должны иметь возможность одновременно решать одну
«десяточку» на разных устройствах. Нажатие, пауза или скрытие страницы одним
участником не должно блокировать или ставить на паузу остальных.

Связанные места текущей реализации:

- UI-блокировка: `static/js/daily_solve_timer.js`, `render()`;
- общий командный actor: `games/views/daily_timing_views.py`, `_resolve_actor()`;
- единственный владелец интервала: `games/daily/timing.py`, `snapshot()` и
  `_takeover_or_continue()`;
- модель: `DailySolveTiming.active_session_id`.

## Новый продуктовый контракт

1. Для командной игры каждая вкладка/устройство имеет собственную временную
   сессию.
2. Сессии одной команды могут работать одновременно.
3. Локальная пауза действует только на текущую сессию. Она не меняет состояние
   таймера у товарищей.
4. Скрытие вкладки, закрытие страницы и потеря heartbeat автоматически ставят
   на паузу только соответствующую сессию.
5. Завершение задания остаётся общим: после решения задания все сессии видят
   completed и больше не считают время.
6. На командной странице никогда не показывается блокирующий экран только
   потому, что другая сессия сейчас активна.
7. Для личного режима можно сохранить защиту от параллельных вкладок, если это
   действительно нужно продукту. Она должна быть явным режимом, а не побочным
   эффектом общей реализации.

## Как считать время

Рекомендуемый вариант — считать **стеночное активное время команды**, то есть
длину объединения активных интервалов всех сессий:

```text
device A:  0 -------- 10       20 ---- 30
device B:       5 -------- 25
team:      0 ----------------------- 30  = 30 секунд
```

Это соответствует смыслу «за сколько команда решила задание» и не умножает
время на число участников. Если нужен отдельный показатель человеческого
усилия, его можно считать позднее как сумму времени сессий, но не использовать
его как время прохождения.

Сервер остаётся источником истины. Важно не пересчитывать полную историю
интервалов на каждом heartbeat: это создаст лишние записи и усложнит гонки.
Лучше хранить у агрегата:

- `accumulated_ms` — уже закрытое командное активное время;
- `active_sessions_count` — число неистёкших running-сессий;
- `team_interval_started_at` — момент перехода счётчика из 0 в 1.

Под row-lock при каждом событии сервер сначала закрывает истёкшие сессии,
затем, если нужно, добавляет время от `team_interval_started_at` до `now` и
меняет счётчик. Пока счётчик больше нуля, новое устройство не сбрасывает
`team_interval_started_at`. При переходе в 0 интервал закрывается. Таким
образом перекрывающиеся сессии автоматически считаются один раз.

Heartbeat бездействующей сессии продлевает её только до последнего принятого
heartbeat, а не до момента обработки запоздалого запроса. Это сохраняет
защиту от накрутки при зависшей вкладке и повторяет текущий lease-контракт.
При завершении фиксируется `frozen_ms`; после этого новые сессии не создаются.

## Предлагаемая модель

Сохранить `DailySolveTiming` как агрегат решения и добавить дочерние сессии,
например `DailySolveTimingSession`:

- `timing` — FK на агрегат;
- `session_id` — UUID, уникальный в рамках timing;
- `status`: `running`, `paused`, `closed`;
- `last_heartbeat_at` и `lease_expires_at`;
- `started_at`, `paused_at`, `closed_at` / причина закрытия;
- `last_seq`, `last_event_id`, небольшой dedupe-набор для идемпотентности;
- `created_at`, `updated_at`.

В агрегате добавить `active_sessions_count` и `team_interval_started_at`.
Heartbeat одной сессии не должен менять статус другой сессии; он меняет общий
счётчик только при переходе этой конкретной сессии между active/inactive.

Отдельный журнал интервалов не нужен для основной логики. Его можно добавить
позже как audit-таблицу, если понадобится разбирать спорные результаты.

Для личного режима можно временно оставить старую схему, но предпочтительнее
перевести оба режима на одну session-модель: тогда различие будет только в
`actor`, а не в логике таймера.

## HTTP/API изменения

- `GET` возвращает агрегированное `accumulated_ms` и состояние текущей сессии:
  `session_status`, `session_id`, `active_sessions_count`, `timing_revision`.
- `start` создаёт или возобновляет только текущую сессию.
- `heartbeat` продлевает только текущую сессию.
- `pause` закрывает/приостанавливает только текущую сессию.
- `resume` возобновляет только текущую сессию.
- `auto_pause` при `visibilitychange` действует только на текущую сессию.
- `complete` атомарно фиксирует агрегат и закрывает все активные сессии.

Поле `is_authoritative` больше не должно управлять доступностью доски в team
mode. Для команды его следует заменить на `session_active`: это только
состояние текущего устройства, а не право пользователя решать.

Каждое событие должно быть идемпотентным по `(session_id, event_id)` и
монотонным по `seq` внутри сессии. Нельзя использовать один `last_seq` на
агрегат: новая вкладка иначе будет конфликтовать с последовательностью другой
вкладки.

В `active_time_ms_for_attempt()` и всех вызовах
`canonical_elapsed_seconds()` нужно читать агрегатное командное время под тем
же правилом, а не искать владельца одной сессии. Иначе UI будет работать
параллельно, но время попыток и leaderboard останутся некорректными.

## UI-поведение

В командном режиме:

- убрать `new-daily-solve__overlay` для foreign session;
- не выставлять `inert` на доску из-за активной сессии другого устройства;
- оставить локальный overlay только для нажатой пользователем паузы, если он
  нужен как подтверждение состояния текущего устройства;
- после локальной паузы показывать кнопку «Продолжить» только на этой странице;
- необязательно показывать ненавязчивый статус вроде «Сейчас решают: 2» — это
  информационный индикатор, а не блокировка.

`BroadcastChannel` и `localStorage` можно оставить для синхронизации вкладок
одного браузера, но они не должны превращать удалённую активность в паузу
текущей страницы.

## Переход

1. Зафиксировать в коде инварианты агрегата: `active_sessions_count >= 0`,
   `team_interval_started_at` существует тогда и только тогда, когда счётчик
   положителен, завершённый агрегат не имеет активных сессий.
2. Добавить session-модель и серверные функции обновления агрегата под row-lock.
3. Покрыть личный и командный режимы доменными тестами без изменения старого
   API.
4. Добавить новый формат snapshot с `session_status`; старые поля временно
   поддерживать для совместимости.
5. Перевести JS: в team mode убрать foreign-lock, сделать pause/resume
   session-scoped.
6. Провести миграцию незавершённых старых командных строк: текущий
   `active_session_id` перенести в одну session-запись, остальные начать как
   paused.
7. Обновить `active_time_ms_for_attempt`, результаты и share-card на новый
   агрегатный snapshot.
8. После браузерного smoke удалить зависимость team mode от
   `is_authoritative` и старого takeover-поведения.

## Обязательные тесты

- два участника одной команды одновременно открыли задание — оба могут вводить
  и отправлять ответы;
- участник A ставит локальную паузу — B продолжает, его время не замораживается;
- A скрывает вкладку — B продолжает, сессия A перестаёт продлеваться;
- A возвращается и нажимает «Продолжить» — возобновляется только A;
- интервалы A и B перекрываются — командное время равно длине объединения, а
  не сумме;
- heartbeat одной сессии не меняет `session_status` другой;
- завершение с одного устройства закрывает остальные сессии и фиксирует время;
- две вкладки одного личного решения сохраняют согласованное выбранное
  поведение;
- устаревший heartbeat не может откатить агрегат или воскресить завершённую
  сессию.
- два heartbeat одновременно под row-lock дают один переход/один зачёт
  интервала;
- истёкшая сессия закрывается, но активная сессия товарища не прерывается;
- ответ `/timing/` и `active_time_ms` в попытке видят согласованную ревизию;
- старый формат строки после миграции не создаёт второй командный таймер.

## Решение, которое нужно подтвердить перед реализацией

Для командного leaderboard и результата использовать объединение активных
интервалов. Это наиболее предсказуемо для пользователей и не зависит от того,
решали ли участники рядом на одном экране или параллельно на нескольких.
