# Архитектура подсчёта времени решения

Статус: описание реализации в `master`, проверено 2026-10-15.

Документ описывает серверный таймер ежедневных игр: от включения на странице до сохранения времени в статистике, известные ограничения и порядок дальнейшего улучшения. Таймер измеряет активное время решения, поэтому его значение намеренно может быть меньше времени от первой до последней попытки.

## Область действия

Таймер подключается через `daily_timing_page_context()` к поддерживаемым страницам ежедневных игр. Сейчас это ежедневные игры разделов, включая Лесенку, Алфавитку, Салатик, Стену, Палиндромы и Замены, а также постоянные случайные Censorly и Alphabetty по hash-ссылкам. Предложения, повторы и уже официально завершённые игры не запускают официальный таймер. Командный режим доступен только для игр, для которых включён командный учёт.

Для случайной игры hash не является идентификатором таймера: endpoint проверяет, что hash принадлежит постоянной случайной игре, затем использует связанную пару `Game` + `TaskGroup`. Поэтому таймер относится к задаче, а не к URL или тексту ссылки. Произвольная ссылка, hash предложения и deferred placement не должны разрешаться как постоянная случайная игра.

Основные места реализации:

- [games/daily/timing.py](../games/daily/timing.py) — модель состояний, применение событий, расчёт и восстановление;
- [games/site/views/daily/timing.py](../games/site/views/daily/timing.py) — HTTP API и разрешение numbered/hash target;
- [static/js/daily_solve_timer.js](../static/js/daily_solve_timer.js) — отображение, запуск, heartbeat, пауза и остановка в браузере;
- [games/daily/completion/completion_coordinator.py](../games/daily/completion/completion_coordinator.py) — атомарное завершение игры и заморозка таймера;
- [games/daily/timing/statistics.py](../games/daily/timing/statistics.py) — чтение завершённых значений для статистики.

## Идентичность и хранение

Каноническая запись — `DailySolveTiming`, уникальная для игры, группы задач, актора и, если применимо, replay slot. Актор — ровно один из:

- пользователь (`user`);
- команда (`team`);
- анонимный игрок (`anon_key`).

Члены команды используют одну строку таймера и несколько независимых `DailySolveTimingSession`: сервер считает объединение активных интервалов команды, не сумму времени её участников. У личного игрока каждая вкладка/устройство тоже получает session lease; параллельное решение на нескольких вкладках не должно удваивать пересекающееся время.

`DailyTimingEvent` хранит принятые действия как журнал для аудита и повторного расчёта. Действия — `start`, `resume`, `heartbeat`, `auto_pause`, `pause`, `complete`. Повторная доставка идемпотентна по event ID; порядок внутри session ограничен sequence number. Снимок `DailySolveTiming` и событие таймера в обычном HTTP пути сохраняются в одной транзакции. Игровое завершение записывает `complete` в той же внешней транзакции, где фиксируются результат и завершение.

Поля времени в снимке:

| Поле | Значение |
|---|---|
| `accumulated_ms` | Уже зачтённое время; во время работы может дополняться открытым интервалом при формировании snapshot. |
| `frozen_ms` | Неизменяемое по смыслу значение завершённой игры; завершение может только увеличить его при восстановлении из журнала. `NULL` означает, что длительность неизвестна. |
| `completed_at` | Серверное время фиксации завершения. |
| session `last_heartbeat_at` | Последнее серверное подтверждение активности конкретной вкладки/устройства. |
| `client_credited_ms` | Часть `accumulated_ms`, начисленная по заявке клиента после протухшего lease, а не по серверным подтверждениям. Ненулевое значение — повод внимательнее посмотреть на результат в лидерборде. |

`claimed_ms` от клиента не является безусловно доверенным источником времени. Время считается по серверным timestamps; клиентская монотонная шкала используется для плавного отображения. Единственное исключение — ограниченное начисление после потерянных heartbeat (см. «Потерянные heartbeat и заявка клиента»).

## Как рассчитывается время

1. После загрузки страницы браузер получает текущий snapshot через `GET` timing endpoint.
2. Если страница видима и таймер не завершён/не поставлен вручную на паузу, браузер отправляет `start` или `resume`. Сервер проверяет игровой контекст, доступ, актора и статус игры, затем выдаёт этой session право считать время.
3. Пока вкладка видима, браузер обновляет циферблат по `performance.now()` и примерно каждые 15 секунд отправляет heartbeat. Браузер скрывает таймер при потере серверной авторитетности.
4. При скрытии вкладки или уходе со страницы UI останавливает локальный ход времени и отправляет `auto_pause` с `keepalive`. При ручной паузе отправляется `pause`; продолжение создаёт/возобновляет lease через `resume`.
5. Принятая игровая попытка (сейчас: попытка и подсказка Цензурки с `timing_session_id`) записывает серверное событие `activity`. Для этой вкладки оно работает как heartbeat: продлевает lease или переоткрывает протухший. Новую session оно не создаёт, ручную паузу не снимает и seq клиента не сдвигает. Через timing endpoint клиент `activity` отправить не может.
6. Сервер закрывает интервалы при паузе, смене владельца, истечении lease или завершении игры. Обычный lease считается stale после 45 секунд без heartbeat. Для heartbeat, который сам пришёл с опозданием, действует дополнительный grace-период 5 секунд для сетевого и планировочного jitter; более поздний heartbeat закрывает старый интервал на последнем подтверждении и не возобновляет lease. Legacy single-session переход дополнительно ограничивает начисление за интервал 60 секундами. Session-based агрегат использует временные границы heartbeat/lease и отдельного общего 60-секундного лимита не имеет. Общий предел одной игры — 12 часов.
7. Завершение результата блокирует строку таймера в общей транзакции, закрывает активные сессии и пишет `complete`. Затем сервер проигрывает журнал и, если журнал даёт большее значение, увеличивает `frozen_ms`/`accumulated_ms`. Больший существующий `frozen_ms` никогда не уменьшается.
8. Статистика читает завершённую длительность из `frozen_ms`. Для старых строк без активной версии таймера применяется исторический fallback по попыткам. Если активная запись существует, но длительность равна нулю или неизвестна, статистика не должна выдумывать точное значение из попыток.

```mermaid
sequenceDiagram
    participant B as Браузер
    participant V as Timing HTTP API
    participant DB as DailySolveTiming + sessions + event ledger
    participant C as Completion coordinator
    B->>V: GET snapshot
    V->>DB: прочитать состояние актора и session
    DB-->>B: snapshot
    B->>V: start / resume
    V->>DB: проверить контекст и записать событие + обновить lease
    DB-->>B: авторитетный snapshot
    loop видимая страница
        B->>V: heartbeat (около 15 секунд)
        V->>DB: продлить lease и записать событие
    end
    B-->>V: pause / auto_pause при уходе со страницы
    C->>DB: завершить игру, закрыть timer, записать complete
    C->>DB: replay журнала; увеличить снимок при доказанном undercount
```

Серверные действия сверяют timestamp и lease, поэтому браузерный циферблат может ненадолго опережать/отставать от зафиксированного значения на время сетевого запроса. После завершения отображается серверный `frozen_ms`.

## Состояния

У таймера есть четыре основных статуса:

- `running` — есть активная session и открытый интервал;
- `auto_paused` — нет активного lease после скрытия/потери страницы или stale heartbeat;
- `manually_paused` — игрок явно остановил решение;
- `completed` — завершение зафиксировано, новые `start`/`resume` не открывают таймер заново.

Если игра завершилась до первого успешного `start`, completion coordinator может создать завершённую строку с `frozen_ms=NULL`. Это sentinel «время неизвестно», не нулевое время. Он также не даёт опоздавшему запросу запуска оживить таймер после завершения.

## Источники истины и восстановление

Для активной версии основным значением для UI и статистики является строка `DailySolveTiming`; `DailyTimingEvent` позволяет проверить и восстановить её, когда журнал полон. Журнал содержит только успешно принятые сервером действия. Он не знает, сколько человек решал до первого `start`, между heartbeat дольше lease или во время недоступности API.

При завершении код сравнивает replay журнала со снимком и исправляет только доказанный undercount. Такое исправление пишет warning `daily_timing_completion_reconciled` с timing/game/task-group IDs, обоими значениями и числом событий. Для исторических строк команда `repair_daily_solve_timing` по умолчанию работает в dry-run; положительные, но заниженные значения рассматриваются только с `--include-underestimates`, а применение требует `--apply`.

Значение `0:00` может означать разные вещи: успешное завершение до старта таймера; активную строку без начисленного интервала; неисправный/устаревший снимок; либо отсутствие достаточных событий для восстановления. Само по себе нулевое значение не доказывает, что игрок решил мгновенно.

## Известные проблемы и ограничения

### Undercount живой строки после протухшего lease (исправлено 2026-10-22)

Для Alphabetty #76 в production у игрока была завершённая строка `frozen_ms=13 284`, тогда как её 15 событий replay давали примерно `200 675` мс. Та же картина у Цензурки #9 (2026-10-21): живая строка `0`, журнал `72 291` мс. За сутки до исправления было около 240 таких reconciliation на всех играх.

Причина: `_apply_to_team_row` читал session до `_team_expire_sessions`. Если expiry в том же запросе помечал эту session stale, `start` видел в памяти `running`, не открывал интервал строки и записывал `running` обратно. После первого протухшего lease строка больше не копила время до завершения, а шар показывал заниженное значение. Теперь session перечитывается после expiry. Тест: `test_start_after_own_lease_went_stale_reopens_the_interval`.

Код reconciliation при завершении и предупреждающий лог теперь есть в `master`. Отдельная management-команда позволяет сначала оценить старые строки dry-run-ом. Production repair следует выполнять только после проверки списка строк и явного решения о применении.

### Исправление возникает только при completion

Пока игра идёт, snapshot читается напрямую и не пересобирается из всего журнала. Поэтому повреждённое активное значение может быть видно до завершения. Следующий шаг — измерить частоту reconciliation warnings и сопоставлять их с timing request errors/lock retries. При подтверждении повторяемости добавить периодический аудит завершённых строк, а для активных — ограниченный диагностический endpoint/задачу, не перестраивающую строку на каждом heartbeat.

### Потерянные heartbeat и заявка клиента

Сеть может терять heartbeat, пока страница видима и игрок решает. В production это выглядело так: `start` раз в минуту, а heartbeat между ними до сервера не доходили. Без подтверждений сервер не начисляет время после `last_heartbeat_at`, и минута пропадает.

Поэтому браузер помнит видимое время с последнего подтверждения (`unconfirmedMs`). Оно копится только пока вкладка видима, не на ручной паузе и не дольше idle-предела. Это время отправляется как `claimed_ms` в следующем `start`/`resume`, а в Цензурке — как `timing_unconfirmed_ms` в попытке. Сервер начисляет его, только если session была закрыта как `stale`, и не больше `min(claimed_ms, now − last_heartbeat_at, 10 минут)`. Если за это время другая вкладка актора подтверждала активность, начисления нет. Начисленное складывается в `client_credited_ms`, пишется лог `daily_timing_client_credit`, и replay журнала повторяет то же правило.

Завысить время так нельзя: заявка ограничена серверным разрывом. Занизить его можно и без этого механизма, если блокировать timing-запросы. Такие строки стоит отслеживать отдельно.

Запросы таймера прерываются через 10 секунд (`AbortSignal.timeout`). Повисший на мёртвом соединении запрос больше не держит очередь полминуты, и повтор успевает уйти.

### Неполный журнал не восстанавливает неизвестные интервалы

Если `start` не дошёл до сервера или страница исчерпала повторы, replay не может восстановить реальную длительность. Протухший lease частично покрывается заявкой клиента (см. выше). Клиент показывает сообщение при многократной ошибке старта, но пользователь всё ещё может продолжить игру. Улучшение: записывать агрегированные метрики start/heartbeat ошибок и видимый статус «время не записывается» до успешного старта; рассмотреть повторный запуск при восстановлении видимости.

### Поздний heartbeat и восстановление lease

Запоздавший heartbeat больше не оживляет истёкшую session: после 45 секунд плюс 5 секунд grace старый интервал закрывается на последнем подтверждённом heartbeat, session помечается stale, а агрегат переходит в `auto_paused`, если других активных session не осталось. Сам heartbeat записывается в журнал, но продолжить учёт можно только новым `resume`/`start`. Клиент показывает overlay с кнопкой «Продолжить», когда ответ подтверждает потерю lease. Небольшие задержки в пределах grace по-прежнему принимаются, включая heartbeat сразу за границей 45 секунд.

Ошибки доставки heartbeat показываются общим предупреждением о несохранённом времени; отдельной агрегированной метрики для клиентских ошибок пока нет. Сервер пишет безопасное событие `daily_timing_sessions_expired` с ID строки, игры и группы, числом закрытых lease и количеством оставшихся активных lease — без actor key и игрового payload. После неясного результата heartbeat клиент требует явного «Продолжить», потому что сервер мог успеть закрыть lease, хотя ответ потерялся. Неудачный первоначальный запуск повторяется после восстановления сети или видимости вкладки, если игрок не ставил игру на ручную паузу. Следующий шаг — собирать агрегированные счётчики клиентских ошибок и долю времени с потерянным lease.

### Завершение случайной игры по hash не имеет полного регрессионного покрытия

Resolver проверяет постоянную Random Censorly/Alphabetty запись и связывает hash с task group; для Censorly страница явно задаёт timing URL, Alphabetty использует canonical URL placement. В `docs/realtime-architecture.md` ранее отмечено отсутствие сквозной проверки: hash страницы запускает правильный акторский таймер, completion замораживает его, а чужой/предложенный hash отклоняется. Добавить endpoint-тесты для обоих игр и один проверочный сценарий от страницы до completion.

### Разные временные шкалы

Локальная анимация опирается на `performance.now()`, серверный расчёт — на wall clock и timestamps БД. Клиентское время передаётся только как дополнительная подсказка; смена системных часов игрока не должна менять официальный результат. Сетевые задержки и переходы видимости могут дать небольшое расхождение в UI. При расследовании сравнивать ledger и серверные времена, а не локальные сохранённые данные браузера.

### Журнал растёт без ограничения

Каждый принятый heartbeat добавляет событие, а reconciliation читает историю целиком. Для обычной игры объём небольшой, но таблица растёт бессрочно и replay дороже для очень длинных сессий. Сначала измерить количество событий на одну игру и длительность replay; затем при необходимости добавить проверяемые контрольные снимки/периодические checkpoints с сохранением возможности аудита. Удалять исходные события без такого checkpoint-контракта нельзя.

## План улучшений

1. **Наблюдаемость:** после выкладки логирования собрать частоту `daily_timing_completion_reconciled`; добавить счётчики ошибок `start`, `heartbeat`, `pause`, lock retry и долю завершений с неизвестным временем. Не логировать anon key или игровой payload.
2. **Зафиксировать hash-пути тестами:** Censorly и Alphabetty, личный/анонимный актор, правильное завершение, отклонение чужих и offer hashes.
3. **Проверить крайние переходы браузера:** старт при медленном API, несколько вкладок, hidden/pagehide с неуспешным keepalive, возврат после lease expiry, завершение с heartbeat в полёте. Для этих сценариев сопоставить JS unit, endpoint и DB ledger assertions.
4. **Закрыть stale-heartbeat риск:** определить желаемую политику после lease expiry; затем закрывать старый интервал на последнем heartbeat и требовать явный resume для новой активности. Проверить задержки чуть выше порога и на минуты.
5. **Разобрать повторяющиеся undercount warnings:** брать row ID и временную последовательность событий; установить, на каком переходе snapshot расходится с ledger. Только после этого выбирать конкретную транзакционную правку.
6. **Оценить стоимость полного replay:** измерить p95 числа событий/времени на завершение. Если есть регрессия, добавить checkpoint или отдельный read model, оставив event ledger источником forensic-аудита.
7. **Историческое исправление:** для конкретного игрока/релиза запускать `repair_daily_solve_timing` сначала без `--apply`; сверять актёра, frozen/recovered и список кандидатов; применять только явно одобренный scope.
