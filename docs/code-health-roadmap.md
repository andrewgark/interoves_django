# План улучшения структуры кода

Цель — постепенно сделать репозиторий более читаемым и консистентным, не
останавливая разработку и не устраивая массовый рефакторинг.

## Зафиксированная исходная точка

- примерно 700 Python-файлов;
- примерно 470 HTML-шаблонов;
- крупные точки концентрации логики: `games/views/new_ui.py`,
  `games/models.py`, `games/admin.py`, `games/recheck.py`;
- одновременно существуют новый и legacy UI;
- текущий тестовый вход — `run_tests.sh`, который уже включает responsive
  lint и проверку inline JavaScript;
- рабочее дерево при создании этого плана было изменено в
  `games/projection_events.py`, а также содержало незатреканные служебные
  файлы. Эти изменения не являются частью плана.

## Этапы

### 1. Базовые правила и наблюдаемость

Статус: начато.

- единый документ разработки и границ слоёв;
- правила для новых изменений и рефакторингов;
- список текущих проверок;
- позже — baseline статического анализа без требования исправить весь legacy.

Критерий готовности: новый агент может понять, где искать код и какие проверки
запустить, не изучая историю проекта.

### 2. Безопасный статический baseline

- выбрать один Python-инструмент для импортов, очевидных ошибок и базового
  style-check;
- сначала только измерить существующие нарушения;
- CI должен не допускать новых нарушений в изменённых файлах;
- массовое исправление старого кода делать отдельными тематическими сериями.

### 3. Первый домен для декомпозиции

Начать с `games/views/new_ui.py`, не меняя URL-контракты:

1. составить карту функций и их вызывающих маршрутов;
2. сгруппировать код по устойчивым областям ответственности;
3. добавить или уточнить тесты существующего поведения;
4. перенести одну группу функций без изменения логики;
5. сохранить фасад совместимости, если он снижает риск импорта;
6. только после нескольких переносов удалить доказанную копипасту.

Не пытаться заранее придумать идеальную конечную структуру.

### 4. Повторяющиеся доменные операции

Искать и объединять только подтверждённые повторы вокруг контекста игры,
доступа, share-ссылок, actor/team state, временных интервалов и JSON payload.
Каждая новая общая операция должна иметь тематическое имя, тест контракта и
одного владельца.

### 5. Интеграции и worker-код

После первого домена отдельно разобрать повторяющиеся retry/error/logging
паттерны в Telegram, payments, recheck и analytics. Интеграционные контракты
и production-sensitive поведение проверять отдельными smoke-тестами.

Отдельно зафиксировать карту актуальных worker-очередей: для каждого worker
указать runtime (ECS/EB), queue и DLQ, CloudWatch log group, типы сообщений и
источник истины для deployment-конфигурации. Legacy EB-описания явно пометить
как legacy, чтобы агент не выбрал их вместо текущего ECS runtime.

### 6. UI-консистентность

Расширить существующие правила new UI: компоненты, tokens, modal, формы,
breakpoints и границы legacy Bootstrap. Новый UI не должен добавлять ещё один
параллельный паттерн.

## Защитные ограничения

- не трогать migrations без функциональной необходимости;
- не смешивать переименование файлов с изменением логики;
- не удалять legacy-код только из-за его возраста;
- не выносить код в общий модуль ради уменьшения числа строк;
- каждый перенос делать маленьким проверяемым коммитом;
- после каждого шага запускать тесты затронутого домена и `manage.py check`;
- перед merge сравнивать публичные URL, webhook и worker-контракты.

## Первые задачи backlog

1. Добавить минимальный статический baseline для изменяемых Python-файлов.
2. Построить карту маршрутов и функций `games/views/new_ui.py`.
3. Выбрать одну группу повторяющейся подготовки контекста и покрыть её
   контрактом.
4. Перенести эту группу в тематический модуль без изменения поведения.
5. Повторить цикл для следующей группы только после проверки первого результата.
6. Создать canonical-карту worker-очередей и синхронизировать её с
   `games/worker_contract.py`, ECS templates и AWS runtime; отдельно описать
   identity queue `interoves-identity` и её DLQ.

Успех измеряется не количеством удалённых строк, а тем, что новые изменения
становятся предсказуемыми, а количество новых нарушений не растёт.
