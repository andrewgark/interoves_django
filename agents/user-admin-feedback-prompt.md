# Промпт: кабинет обратной связи (багрепорты, ответы админа, мои задания)

Сейчас пользователь может **отправить** багрепорт по заданию, но **некуда вернуться**: нет списка своих репортов, нет статусов, нет ответа от админа. Параллельно уже есть пользовательское создание лесенок и алфавиток с отправкой Андрею — списки живут на отдельных URL, но из Профиля туда не попасть. Нужно структурировать «общение пользователя с админом по поводу фидбека», не ломая существующую логику.

**Этот промпт пока не выполнять целиком без аудита.** Сначала изучи код, затем итерациями реализуй.

---

## Проблема глазами пользователя

1. На странице задания есть «Сообщить о проблеме» → модалка → POST → «Спасибо! Репорт отправлен.» Дальше репорт исчезает из жизни пользователя.
2. Админ видит репорт в Telegram, Django admin и `/support/pending/`, ставит Pending / Reviewed / Dismissed. Пользователь этого не видит.
3. `BugReport.admin_notes` — заметки админа, **не** публичный ответ. Переписки нет.
4. Есть кнопки «Сделать новую лесенку» (`/create_ladder/`) и «Создать свою алфавитку» (`/create_alphabetty/`). На этих страницах **уже есть** список своих офферов со статусами (черновик / отправлена / принята / на доработке) и односторонний комментарий «для Андрея» + `admin_note` при возврате. Из Профиля на эти списки ссылок нет.
5. Потенциально появятся другие типы пользовательских заданий с тем же паттерном «создал → предложил в ежедневную → статус». Кабинет должен это выдержать без переделки профиля каждый раз.

Нужно: место «около Профиля», где видны **обращения** (багрепорты + переписка) и **мои созданные задания** (лесенки, алфавитки, позже другие виды).

## Что уже есть (сохранить и продолжить)

Не придумывай параллельную систему тикетов. Доменная логика уже есть — её надо открыть пользователю и аккуратно нарастить перепиской.

### Багрепорты

| Что | Где |
|-----|-----|
| Модель | `games.models.BugReport`: `task`, `game`, `team`, `user`, `anon_key`, `text`, `page_url`, `time`, `status` (`Pending` / `Reviewed` / `Dismissed`), `admin_notes` |
| Отправка с сайта | `games.views.new_ui.new_bug_report` (`POST /bug-report/<task_id>/`), модалка в `static/templates/new/task_group.html` |
| Telegram админу | `post_save` → `notify_new_bug_report` (`games/telegram/signals.py`, `notify.py`): текст + inline-кнопки Reviewed / Dismiss |
| Колбэки TG | `games/telegram/callbacks.py` `_handle_bug` |
| Support | очередь `/support/pending/` (`games/support/services/pending.py`), действия `bug_reviewed` / `bug_dismissed` (`games/support/actions.py`) |
| Django admin | `BugReport` + proxy `PendingBugReport` |
| Гость → аккаунт | `anon_key`; перенос в `games/anon_migrate.py` (`migrate_anon_attributions`) и `account_merge` |

Важно: в **командном** режиме `new_bug_report` пишет `team`, а `user=None`. Из‑за этого «мои репорты» по `user=` пустые для командной игры. При сохранении, если пользователь залогинен, **всегда писать `user`**, `team` оставлять как сейчас. Старые строки без user — решить явно (см. итерацию 1).

### Предложения заданий (уже пользовательские списки)

| Тип | Список (это и есть «мои …») | Модель / статусы | TG админу |
|-----|-----------------------------|------------------|-----------|
| Лесенка | `/create_ladder/` | `LadderOffer`: draft / sent / accepted; `comment`, `admin_note`, `share_hash` | `notify_new_ladder_offer` при send |
| Алфавитка | `/create_alphabetty/` | `AlphabettyOffer` — тот же каркас | `notify_new_alphabetty_offer` |

Support: `/support/ladders/`, `/support/alphabetty/` (accept / revision с `admin_note`).  
Не дублировать эти списки новой страницей «мои лесенки». С Профиля — **ссылки на уже существующие URL**.

### Профиль и навигация

- `/profile/` — `games.views.new_ui.new_profile`, шаблон `static/templates/new/profile.html`: имя, фото, Telegram-хэндл, таймзона, соц. аккаунты. Ссылок на репорты/офферы нет.
- В шапке (`new/base.html`) Профиль — иконка + пункт меню. **Не** добавлять в основной nav пять новых пунктов.
- Рекомендуемое место ссылок: **блок на странице Профиля** после формы/аккаунтов (секция вроде «Мои материалы и обращения»). Опционально — короткая ссылка из дровера рядом с «Профиль», не в quick-nav.

### Telegram: админ vs пользователь

- `send_admin_message` шлёт **только** в admin-чат (`TELEGRAM_ADMIN_CHAT_ID`). Пользователю бот сейчас почти ничего не пишет (кроме привязки `/start <token>` и публичных `/des`).
- Для DM пользователю нужен **chat id** = `Profile.telegram_user_id` (верифицированная identity через бота или Telegram login). Поле `telegram_handle` — публичный @username, **не** id чата; по нему слать нельзя.
- Вебхук (`games/telegram/webhook.py`): callback-кнопки только из admin-чата; произвольный текст не из admin-чата игнорируется. Переписка «ответил reply’ем в Telegram на карточку бага» — отдельная итерация, не блокер сайта.

Связанные сущности на потом (не в первый срез, но не сломать): `AlphabettyDictSuggestion`, заявки на билеты, корпоративные заявки.

## Целевая модель продукта

Три слоя, не один «универсальный inbox»:

1. **Кабинет у Профиля** — навигация: обращения, мои лесенки, мои алфавитки, задел под новые типы.
2. **Обращения** — список багрепортов пользователя + тред по каждому.
3. **Мои задания** — существующие `/create_ladder/`, `/create_alphabetty/` (+ будущие `/create_<kind>/`).

Не смешивать в одну ленту баги и черновики лесенок. Общее только место входа и паттерн «пользователь написал → админ ответил → снова пользователь».

### Переписка по багрепорту

Минимальный тред на репорт, не полноценный мессенджер:

- Пользователь пишет первое сообщение при создании (текущий `text`) и может писать дальше, пока репорт не закрыт окончательно (правило закрытия — зафиксировать; разумный дефолт: можно писать в Pending и Reviewed, в Dismissed — нет или только «открыть снова» — выбрать одно и тестировать).
- Админ отвечает текстом, который **видит пользователь**. `admin_notes` оставить приватными.
- Статусы Pending / Reviewed / Dismissed сохранить. Ответ админа не обязан сам менять статус; смена статуса может сопровождаться опциональным публичным комментарием.
- На сайте тред — источник правды. Telegram — транспорт уведомлений.

### Уведомления Telegram (логичное продолжение)

| Событие | Куда |
|---------|------|
| Новый репорт | как сейчас, admin-чат + кнопки статуса |
| Новый ответ **пользователя** в треде | admin-чат, ссылка на репорт/админку/сайт |
| Новый ответ **админа** | на сайт всегда; в Telegram пользователю **если** есть `telegram_user_id` |
| Смена статуса без текста | не обязательно слать пользователю; достаточно увидеть в списке |

Нет `telegram_user_id` — тред на сайте всё равно работает. Не требовать Telegram для багрепорта (сейчас гости могут репортить с `anon_key`).

Не строить отдельный user-facing Telegram-бот с командами «/bugs». Сайт — UI, TG — пинги.

### Расширяемость кабинета

Не делать плагинный реестр в v1. На Профиле — явный список ссылок + короткий комментарий в коде/доке: новый тип пользовательских заданий добавляет пункт («Мои …» → `/create_<kind>/`), когда появится тот же offer-flow. Унифицировать `LadderOffer`/`AlphabettyOffer` в одну полиморфную модель **не** надо.

Переписку на офферах в v1 не делать: там уже `comment` + `admin_note`. Если позже понадобится тред — тот же примитив сообщений, что у багов.

## Порядок работы

### Итерация 0 — аудит (без кода, кроме заметок)

Короткий отчёт:

1. Подтверди точки выше; добавь пропущенные URL/шаблоны.
2. Как сейчас атрибутировать репорт: user vs team vs anon_key; что попадёт в «мои».
3. Можно ли слать DM: где выставляются `telegram_user_id` / `telegram_verified` (`telegram_linking`, OIDC, `sync_telegram_identity`).
4. Где в профиле/nav логичнее блок ссылок (не раздувая шапку).
5. Предложи модель сообщений: отдельная `BugReportMessage` vs обобщённый `FeedbackMessage` с FK/GFK. Для v1 предпочтительна **простая** `BugReportMessage` (`report`, `author_user` nullable, `author_role` user|admin, `text`, `created_at`, опционально id TG-сообщения). Первый `BugReport.text` либо остаётся каноническим первым сообщением, либо копируется в тред один раз — не держать два расходящихся источника.
6. План итераций 1–3. Пока не пили всё сразу.

### Итерация 1 — список репортов + кабинет на Профиле

Пользователь видит свои обращения и находит свои лесенки/алфавитки.

- Страница списка (например `/profile/reports/` или `/feedback/` — имя согласовать с `/profile/`, login_required + guest-ключ если решите поддерживать анонов).
- Карточка: игра, номер/название задания, дата, статус, превью текста, ссылка на задание (`page_url` / `task_play_url`).
- Страница репорта: полный текст, статус, ссылка на задание. В этой итерации ещё без формы ответа, если так проще; лучше сразу заложить шаблон треда.
- После успешного сабмита модалки — ссылка «Мои обращения» / на этот репорт, не только «Спасибо».
- На `/profile/` — секция ссылок:
  - Мои обращения (багрепорты)
  - Мои лесенки → `/create_ladder/`
  - Мои алфавитки → `/create_alphabetty/`
- При создании репорта залогиненным всегда заполнять `user`.
- Тесты: список не показывает чужие репорты; статусы; командные репорты с user; anon migrate по-прежнему работает.
- UI: new UI, статусы читаемые по-русски (не сырой `Pending`).

### Итерация 2 — переписка на сайте + TG-пинги

- Модель сообщений, миграция, админка (inline к репорту).
- Пользователь пишет ответ в треде; админ пишет ответ (Django admin и/или support — минимум один рабочий путь в этой итерации).
- `admin_notes` не показываются пользователю.
- TG: новое сообщение пользователя → admin-чат; ответ админа → DM если есть `telegram_user_id`.
- Не слать повторный «новый репорт» на каждый reply; формат писем отличаться от `format_bug_report_message`.
- Кнопки Reviewed/Dismiss на исходном сообщении оставить; они меняют статус, не подменяют тред.
- Тесты на модели, права, notify (по аналогии с `games/tests/test_telegram.py`, `test_telegram_notify.py`).

### Итерация 3 — админский UX и (опционально) TG reply

- Support: у pending-бага не только Reviewed/Dismiss, но и короткое поле ответа (или ссылка на тред).
- Telegram: кнопка/команда «ответить» сложнее callback_data лимита 64 байт — либо ссылка на сайт/админку в тексте карточки, либо reply на сообщение бота в admin-чате, который парсится в `BugReportMessage`. Не ломать существующие `bug:reviewed:id` / `bug:dismiss:id`.
- Ссылка на пользовательский тред в `format_bug_report_message`.
- Если останется время: бейдж/точка на иконке Профиля, если есть непрочитанный ответ админа (не обязательно realtime; достаточно флага на репорте). Realtime не обязателен.

## Чего не делать

- Не заменять BugReport общим Zendesk-like inbox.
- Не удалять статусы, support pending, admin proxy, TG-кнопки.
- Не использовать `admin_notes` как публичный ответ.
- Не требовать Telegram для просмотра треда.
- Не слать пользователю по `telegram_handle` (только `telegram_user_id`).
- Не дублировать списки офферов; не унифицировать LadderOffer/AlphabettyOffer.
- Не тащить в v1 словарь алфавитки, билеты, корпоративные заявки.
- Не добавлять React/чат-виджеты.
- Не класть 5 пунктов в основное меню шапки.
